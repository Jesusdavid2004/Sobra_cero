# ADR 0007: Rescue analysis as a separate gRPC service

- Status: Accepted

## Context

The rescue plan needs expected sales, surplus and reason codes. The class
material asks for a real service boundary with a generated contract. Reservations
and the browser must not depend on that analysis being available.

## Decision

- Extract only the stateless analysis (forecast plus the deterministic rescue
  rule) into `app-analysis/`, called over native gRPC from FastAPI. The service
  has no database access and never receives shop identifiers; FastAPI authorizes
  the owner and sends a snapshot.
- The contract lives in `proto/` and the stubs are generated by
  `scripts/generate_grpc.py` and committed; CI regenerates them and fails on a
  diff.
- Pure modules (`domain/`, predictors) are reused from `app-backend` by building
  the image from the repository root, so there is one implementation of the
  math. `LocalRescueAnalyzer` is the code the service executes and the in-process
  fallback.
- If the service is `UNAVAILABLE` or exceeds the deadline, the plan is created
  locally and recorded as `local_fallback` with an `analysis_fallback` audit
  event. Invalid requests and authentication failures are not retried locally.
- Callers authenticate with a shared token in metadata, compared in constant
  time. The service is meant for a private network. This is not mutual TLS.
- New dependencies: `grpcio`, `grpcio-health-checking`, `grpcio-tools` (stub
  generation) and `protobuf`, pinned in `requirements.txt`. `grpcio-tools` is in
  the same file as the other dev tools to match the existing convention.

## Consequences

- One more process to deploy and monitor. With `ANALYSIS_GRPC_TARGET` empty the
  application behaves as before.
- No claim is made that gRPC is faster than the in-process call; latency and
  status are logged per call so a fair comparison can be done later.
- Browsers do not call this service; gRPC-Web is out of scope.

# Phase 2 audit and design: gRPC rescue analysis service

Read-only audit on 2026-11-10 of the backend after Phase 1 (`05eb221`).

## Findings

- The analysis math already lives behind a port: `PredictionModel`
  (`WeightedMovingAveragePredictionModel`, `WeekdaySalesForecastModel`) plus the
  pure `decide_rescue` rule in `domain/rescue.py`. `GenerateRescuePlan` calls both
  in-process, so the boundary can be moved without changing the use case's
  behavior.
- The predictors only need a sales history, the stock, the horizon and (for the
  trained model) seven weekday factors. They need no database access, so a
  separate service can run with no DB and no ability to read other shops' data.
- `grpcio`, `grpcio-tools` and `protobuf` are not in `requirements.txt` and are
  not installed. They are new dependencies and need an ADR.
- Railway builds `app-backend/Dockerfile`. A second Railway service is needed for
  the analysis process; I cannot verify the Railway project from here, so the
  deployment steps below are instructions, not a verified result.
- No request-id or structured-logging convention exists yet for cross-service
  calls.

## Design

**Boundary.** FastAPI keeps authentication, authorization and lot snapshots. The
analysis service never receives a shop id and never touches the database: the
request carries a snapshot (stock, discount, horizon hours, sales history and,
if a trained model is active, its weekday factors) and returns numbers and reason
codes. It writes nothing.

**Contract** (`proto/rescue_analysis.proto`, package `sobracero.analysis.v1`)
- `rpc AnalyzeLot(AnalyzeLotRequest) returns (AnalyzeLotResponse)` (unary).
- Request: `request_id`, `available_quantity`, `current_discount_percent`,
  `horizon_hours`, `history[]` (`sales_date`, `units_sold`, `had_promotion`),
  optional `weekday_factors[7]` + `model_version`.
- Response: `expected_sales`, `surplus_units`, `action`, `proposed_discount_percent`,
  `reasons[]` (stable codes), `model_version`, `rule_version`.
- Semantic validation on the server (`INVALID_ARGUMENT`, generic messages):
  quantity > 0, horizon in range, at most 365 history rows, 7 finite
  non-negative factors. `AnalyzeShop` and streaming are not built now; I will add
  them in the phase that has a consumer (the prioritized shop panel) so there is
  no unused code.

**Backend changes**
- New port `RescueAnalyzer` in `application/ports.py`. `GenerateRescuePlan`
  depends on it instead of `PredictionModel` + `decide_rescue`.
- Adapters in `infrastructure/analysis/`: `LocalRescueAnalyzer` (today's code,
  also the fallback) and `GrpcRescueAnalyzer` (explicit deadline, request id and
  token in metadata, status-code to typed-exception mapping).
- If the service is unreachable or times out, the plan is still produced by the
  local analyzer and is marked `analysis_source = "local_fallback"` in its
  stored inputs and in an audit event, so the fallback is identifiable. Only
  `UNAVAILABLE` and `DEADLINE_EXCEEDED` fall back; `INVALID_ARGUMENT` and
  authentication errors surface as errors. Reservations never depend on this
  service.
- Settings: `ANALYSIS_GRPC_TARGET` (empty = local analyzer, the default so
  current deployments are unchanged), `ANALYSIS_GRPC_TIMEOUT_SECONDS` (default
  2), `ANALYSIS_SHARED_TOKEN`.
- Latency, status and request id are logged per call (no personal content). No
  performance claim is made.

**Service** (`app-analysis/`)
- Own Dockerfile and `requirements.txt`; entry point `server.py` with a gRPC
  health service. It reuses the existing pure modules (`domain/`, predictors)
  from `app-backend` so there is one source for the math; the Docker build
  context is the repository root.
- Authenticates callers with the shared token in metadata
  (`UNAUTHENTICATED` otherwise). Intended for a private network; Railway's
  private networking does not give mutual TLS, so this is token auth over a
  private network, not a claim of end-to-end encryption.

**Reproducibility.** Stubs are generated by `scripts/generate_grpc.py` (a
single cross-platform Python script) from the `.proto` into
`app-backend/app/infrastructure/analysis/generated/` and committed; CI
regenerates and fails on a diff. `AnalyzeShop` (at most 50 lots, ranked by
surplus ratio) is included in the contract and the service at the user's
request; the API does not expose it yet.

**Tests** (real in-process gRPC server on a random localhost port, not mocks)
- Same inputs give the same plan through `LocalRescueAnalyzer` and over gRPC.
- Server stopped: plan still created, marked `local_fallback`, event recorded.
- Slow server (deadline exceeded) falls back; `INVALID_ARGUMENT` and missing or
  wrong token do not fall back.
- Server validation rejects malformed requests; request id round-trips.
- Existing Phase 1 tests keep passing with the local analyzer.

## Out of scope

Streaming, `AnalyzeShop`, gRPC-Web or browser access, mTLS, REST-vs-gRPC
benchmarks, and the rendering/WebSocket phases.

## Deployment (to be done by you in Railway, not verified here)

Create a second service from this repo with Dockerfile path
`app-analysis/Dockerfile` and the repository root as build context, no public
domain, and `ANALYSIS_SHARED_TOKEN` set. On the API service set
`ANALYSIS_GRPC_TARGET=<service>.railway.internal:<port>` and the same token.
